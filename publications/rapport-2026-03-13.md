### Hooks

**Voorstel:** Implementeer PreToolUse hooks voor deterministische kwaliteitscontrole
**Bron:** Blake Crosley — [Claude Code Hooks Tutorial: 5 Production Hooks From Scratch](https://blakecrosley.com/blog/claude-code-hooks-tutorial)
**Type:** fundamenteel
**Toelichting:** Hooks transformeren richtlijnen in afgedwongen regels. PreToolUse hooks inspecteren en kunnen acties blokkeren vóórdat Claude ze uitvoert (bijv. voorkomen dat Claude productiebestanden wijzigt), terwijl PostToolUse hooks valideren en formatteren na afloop. Dit geeft je deterministische controle over wat Claude met je codebase doet — iets dat CLAUDE.md-instructies alleen niet kunnen garanderen.

```yaml
# Voorbeeld: PreToolUse hook die productiebestanden beschermt
# In .claude/settings.json:
hooks:
  PreToolUse:
    - matcher: "Edit|Write"
      command: |
        # Lees event data van stdin
        INPUT=$(cat)
        FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
        if [[ "$FILE" == *"/production/"* ]]; then
          echo '{"decision":"block","reason":"Productiebestanden zijn beschermd"}'
          exit 0
        fi
        echo '{"decision":"allow"}'
```

**Voorstel:** Stel notificatie-hooks in voor taakafronding
**Bron:** Anthropic — [Automate workflows with hooks - Claude Code Docs](https://code.claude.com/docs/en/hooks-guide)
**Type:** klein
**Toelichting:** Een eenvoudige hook die een desktopnotificatie stuurt wanneer Claude klaar is met een langlopende taak, zodat je ondertussen aan andere dingen kunt werken.

# 3. Identificeer performance bottlenecks

### Git-integratie

**Voorstel:** Combineer Claude Code hooks met git hooks (Husky/pre-commit) voor dubbele kwaliteitsgrenzen
**Bron:** DEV Community — [Git Hooks with Claude Code: Build Quality Gates with Husky and Pre-commit](https://dev.to/myougatheaxo/git-hooks-with-claude-code-build-quality-gates-with-husky-and-pre-commit-27l0)
**Type:** fundamenteel
**Toelichting:** Een cruciaal onderscheid: git hooks draaien wanneer jij git gebruikt, Claude Code hooks draaien wanneer Claude tools gebruikt (inclusief git). Door beide lagen te combineren, creëer je kwaliteitsgrenzen die zowel menselijke als AI-gegenereerde code afdekken. Dit voorkomt dat Claude direct naar `main` pusht of commits maakt die niet aan je standaarden voldoen.

```yaml
# Twee-laagse kwaliteitscontrole:
#
# Laag 1: Claude Code hook (PreToolUse)
# - Blokkeer commits naar beschermde branches
# - Forceer conventionele commit-berichten
#
# Laag 2: Git hook (via Husky)
# - Draai linters en formatters op staged files
# - Voer unit tests uit voor commit
#
# Installatie:
# npx husky init
# echo "npx lint-staged" > .husky/pre-commit
```

**Voorstel:** Begrijp het verschil tussen Claude Code hooks en git hooks
**Bron:** JP Caparas, Reading.sh — [Claude Code hooks: a bookmarkable guide to git automation](https://reading.sh/claude-code-hooks-a-bookmarkable-guide-to-git-automation-11b4516adc5d)
**Type:** klein
**Toelichting:** Claude Code hooks zijn middleware voor je AI-agent — ze regelen wat Claude met git doet. Git hooks regelen wat er gebeurt wanneer git-commando's worden uitgevoerd, ongeacht de bron. Beide zijn complementair, niet vervangbaar.

### Multi-file Editing & Refactoring

**Voorstel:** Gebruik Plan Mode voor complexe multi-file refactoring
**Bron:** DataCamp — [Claude Code Plan Mode: Design Review-First Refactoring Loops](https://www.datacamp.com/tutorial/claude-code-plan-mode)
**Type:** fundamenteel
**Toelichting:** Plan Mode lost het kernprobleem van multi-file wijzigingen op: zonder plan maakt Claude ad-hoc wijzigingen die inconsistenties veroorzaken. Met Plan Mode analyseert Claude eerst de volledige codebase, creëert een gestructureerd plan, en voert pas daarna wijzigingen door. Dit is essentieel voor refactoring van meer dan 3-4 bestanden tegelijk.

```yaml
# Workflow voor multi-file refactoring:
# 1. Start met: "plan de refactoring van [component]"
# 2. Review het plan — Claude toont alle betrokken bestanden
# 3. Pas het plan aan indien nodig
# 4. Geef goedkeuring om het plan uit te voeren
# 5. Claude past wijzigingen consistent toe over alle bestanden
```

## Paradigma-check

### 1. Skills vervangen Commands — definitief
De verschuiving van legacy slash commands naar Skills is niet langer optioneel. Meerdere bronnen deze week bevestigen dat Skills alles doen wat commands doen, plus auto-triggering en ondersteunende bestanden. **Als je nog commands gebruikt, is nu het moment om te migreren.**

### 2. Enkelvoudige sessies worden multi-agent teams
Agent Teams, async sub-agents, en Claude Flow wijzen allemaal in dezelfde richting: de toekomst van Claude Code is niet één sessie die alles doet, maar gecoördineerde teams van specialisten. Dit stelt de aanname ter discussie dat je één CLAUDE.md en één sessie nodig hebt per taak.

### 3. "Think before code" als tegenwicht voor snelheid
De populariteit van de "think before code"-benadering suggereert dat de community een correctie doormaakt: snelheid van codegeneratie is minder waardevol dan architecturele correctheid. Dit stelt de gangbare praktijk ter discussie om Claude direct te laten coderen en achteraf te corrigeren.

### 4. 1M token context verandert de spelregels
Met Opus 4.6's 1M token contextvenster vervalt de noodzaak om context agressief te managen voor middelgrote projecten. Dit stelt de aanname ter discussie dat je altijd compact moet werken en context moet minimaliseren — voor bepaalde taken kun je nu bewust meer context laden.

### 5. Deterministische hooks vs. probabilistische instructies
De groeiende nadruk op hooks (van 7 naar 14 lifecycle events, plus async hooks) weerspiegelt een fundamenteel inzicht: voor kritieke kwaliteitsregels zijn deterministische afgedwongen controles betrouwbaarder dan instructies in CLAUDE.md die Claude *waarschijnlijk* zal volgen. **Alles wat je absoluut wilt afdwingen, hoort in hooks — niet in markdown.**
